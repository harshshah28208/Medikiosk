# AUDIT.md

| Feature | Status | Evidence | Problem | Required Fix |
| ------- | ------ | -------- | ------- | ------------ |
| AI Conversation Engine - Dynamic Questioning | PARTIALLY IMPLEMENTED | Backend uses Groq AI Provider to generate dynamic questions based on clinical state and history. Frontend IntakePage has hardcoded touch options and question translation logic. | Frontend overrides AI-generated questions with hardcoded logic in `handleLanguageSwitch` and `translateQLocal`. This breaks the dynamic nature of the AI and may lead to inconsistent questioning. | Remove frontend hardcoded question translation and rely solely on backend AI for question generation and translation. Frontend should only display AI-provided questions and touch options. |
| Persistent Clinical State | IMPLEMENTED — NOT VERIFIED | Backend ClinicalState model tracks symptoms, history, lifestyle, etc. Domain completeness tracking exists. | Frontend does not persist clinical state to backend after each answer; relies on localStorage and resumes from localStorage. Risk of state loss if localStorage cleared. | Ensure every patient answer is sent to backend via `api.conversation.sendMessage` and backend updates the ConversationSession's clinicalState. Frontend should load clinical state from backend on resume, not localStorage. |
| New Case vs Follow-up Separation | PARTIALLY IMPLEMENTED | Backend conversation routes attempt to match prior visits by care path and complaint similarity. However, uses `findFirst` without proper scoping in some places (e.g., line 623: `prisma.conversationSession.findFirst` without filtering by patientId and carePath). | Risk of loading wrong prior session (e.g., from another patient or different care path) leading to incorrect follow-up context. | Replace `findFirst` with `findUnique` or `findMany` with proper filters: patientId, carePath, and visitId exclusion. Ensure follow-up only loads prior visit in same care path and for same patient. |
| Longitudinal History | PARTIALLY IMPLEMENTED | Doctor Patient-360 view aggregates visits. However, frontend PatientPortalPage may only show latest visit due to use of `take: 1` or `findFirst` in API fallbacks. | Evidence: In `api.ts`, many endpoints have `.catch(() => { return demo data; })` which may return only one item. | Remove demo fallbacks and ensure backend returns all visits for a patient. Fix frontend to display array of visits, not just first. |
| Language Switching Mid-Assessment | BROKEN | Frontend `handleLanguageSwitch` attempts to translate messages locally and then sync with backend. However, local translation is incomplete and may corrupt clinical state (e.g., translating numbers, measurements). | Local translation does not preserve negation, numbers, measurements correctly. Example: "I don't have vomiting." may become incorrect after translation. | Remove frontend local translation. Rely on backend `/conversation/:sessionId/switch-language` endpoint which uses AI to translate entire conversation accurately. Frontend should only call the backend endpoint and replace messages with returned translatedMessages. |
| Voice Input Handling | PARTIALLY IMPLEMENTED | Frontend uses Web Speech API for voice input and output. However, on voice error, frontend does not allow retry without losing state. | Voice errors cause `voiceError` state but no automatic retry; user must manually tap mic again. | Implement automatic retry on voice error after a short delay, or at least retain the transcribed text in input box for user to edit and resend. |
| AI Completion Detection | PARTIALLY IMPLEMENTED | Backend sets `isComplete` based on AI output or keyword matching. Frontend shows completion card when `isComplete` is true. | Frontend also has hardcoded completion triggers (e.g., matching strings like "proceed|appointment|consultation") which may not align with AI's completion decision. | Remove frontend hardcoded completion triggers. Rely solely on backend's `isComplete` flag to determine when to show completion UI. |
| Summary Generation | IMPLEMENTED — NOT VERIFIED | Backend uses AI Provider to generate clinical summary from state. | Frontend ReviewPage may not display summary correctly if summaryJson is not parsed. Evidence: In `PatientReviewPage.tsx` (not inspected but likely) may assume summary is a string. | Ensure summary is parsed from JSON and displayed in a structured format appropriate to care path and specialty. |
| Red Flag Detection | IMPLEMENTED — NOT VERIFIED | Backend uses RedFlagEngine to evaluate state and patient input. | Frontend displays red flag alert but may not persist red flags in clinical state for summary. | Ensure red flags are added to clinical state.redFlags and included in summary generation. |
| Data Persistence - Every Answer Stored | PARTIALLY IMPLEMENTED | Backend stores each ConversationMessage. However, clinical state is stored as JSON in ConversationSession.clinicalState and updated only after each turn. | Risk of losing intermediate state if client crashes before sending message to backend. | Implement optimistic update: frontend updates local UI immediately, but also sends message to backend in background. If send fails, show error and allow retry without losing message. |
| Multilingual Support - Hindi/Gujarati | PARTIALLY IMPLEMENTED | Backend and frontend support language switching. However, frontend language switcher only changes UI language, not necessarily the AI language if not synced. | Frontend `handleLanguageSwitch` attempts to sync but may fail silently, leading to mismatch between UI language and AI language. | Ensure backend language switch endpoint is called and frontend updates its language state only after successful backend response. |
| Security - IDOR Prevention | PARTIALLY IMPLEMENTED | Backend routes use `req.user.id` to filter queries. However, some routes may not properly scope to patient (e.g., document routes). | Evidence: In `api.ts`, `documents.getForPatient` uses `/documents/${patientId}` without checking if patientId matches logged-in patient. | Add authorization middleware to all patient-scoped routes to verify that the requested patientId matches the authenticated user's patientId. |
